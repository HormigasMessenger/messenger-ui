# Secret chats & calls — end-to-end encryption design

This document describes how Hormiga's **opt-in secret chats** and **end-to-end-authenticated
calls** work: the keys, the algorithms, the multi-device model, and the trust boundary — with
pointers to the primary specifications and to the source that implements each part.

It is the engineering companion to the OpenSpec change
[`openspec/changes/e2ee-device-resolution`](../openspec/changes/e2ee-device-resolution/proposal.md)
and the earlier [`e2ee-call-signaling`](../openspec/changes/e2ee-call-signaling/proposal.md).

> **One-line model:** identity is a *device*, not a person; the directory hands out public keys and
> is closed against MITM only by out-of-band **safety numbers**; sessions are pairwise (one Double
> Ratchet per peer device); the sender caches sessions and lazily re-resolves devices; message
> plaintext lives only locally, for 7 days. Everything cryptographic runs on the client — the
> server sees only ciphertext.

---

## 1. Threat model & trust boundary

- **Adversary:** an untrusted or compromised **messenger server** (and network) that can read,
  drop, reorder, replay, or forge any relayed frame.
- **Defended:** message and call *content* confidentiality/integrity against that server.
- **Not defended by the protocol alone:** the **key directory** is a *trusted* key distributor by
  construction — it could hand out a substituted public key (active MITM). That residual risk is
  closed **only** by users comparing **safety numbers** out-of-band (§5). This is the same design
  point as Signal: the server is untrusted for content, the directory is trusted for distribution,
  and safety numbers are the human check.
- **Library:** [`@privacyresearch/libsignal-protocol-typescript`](https://github.com/privacyresearch/libsignal-protocol-typescript)
  (a TypeScript port of libsignal). All primitives are **Curve25519**; randomness comes from the
  browser CSPRNG (`crypto.getRandomValues`, via the library's curve implementation).

## 2. Keys: Identity, Signed PreKey, One-Time PreKeys

All three are generated on the device via libsignal's `KeyHelper`
([`lib/provisioning.ts`](../front/src/features/e2ee/lib/provisioning.ts)). **Private halves never
leave the device**: they are stored in IndexedDB wrapped under a **non-extractable AES-GCM
device-key** ([`lib/signalStore.ts`](../front/src/features/e2ee/lib/signalStore.ts),
[`lib/deviceKey.ts`](../front/src/features/e2ee/lib/deviceKey.ts)). Only public halves (plus the
SPK signature) are published to the directory.

| Key | Generated by | Lifetime | Role |
|---|---|---|---|
| **IK** — Identity Key | `KeyHelper.generateIdentityKeyPair()` | once; **never rotated** | stable device identity; anchors the safety number |
| **SPK** — Signed PreKey | `KeyHelper.generateSignedPreKey(IK, id=1)` | rotated on every startup republish | medium-term prekey, **signed by IK** |
| **OPK** — One-Time PreKeys | `KeyHelper.generatePreKey(id)` ×N | **single-use**, pool of 20, replenished | per-handshake one-time prekey |
| **LRK** — Last-Resort PreKey | `KeyHelper.generatePreKey(reservedId)` | reusable; **stable** (not rotated) | served when the OPK pool is empty (§6) |

- **SPK signature** = `Sign(IK_priv, SPK_pub)` (XEdDSA over Curve25519 — see
  [XEdDSA spec](https://signal.org/docs/specifications/xeddsa/)). A fetcher verifies it with the
  published `IK_pub`, binding the SPK to the identity.
- **OPK ids** are drawn from a **persisted monotonic floor** so an id is never reused across the
  device's life (`signalStore.allocatePreKeyIds`) — a reused id would let the server drop a fresh
  public and keep a stale one.
- **deviceId** = `crypto.randomUUID()`; it identifies the device row in the directory (not a
  cryptographic value).

**Published bundle** (`provisioning.buildAndPublish` → `POST /key-directory/v1/keys`):
```jsonc
{ "deviceId", "identityKey": IK_pub,
  "signedPreKey": { "id", "publicKey": SPK_pub, "signature" },
  "oneTimePreKeys": [ {"id","publicKey"}, ... ],
  "lastResortPreKey": {"id","publicKey"} }
```

## 3. Session establishment — X3DH

The first message to a peer device runs **X3DH** (Extended Triple Diffie-Hellman,
[spec](https://signal.org/docs/specifications/x3dh/)) to agree an initial shared secret.

The sender fetches the peer's bundle (`IK, SPK, one OPK`) and computes, with a fresh ephemeral key
`EK`:
```
DH1 = DH(IK_A, SPK_B)
DH2 = DH(EK_A, IK_B)
DH3 = DH(EK_A, SPK_B)
DH4 = DH(EK_A, OPK_B)          # omitted if the peer's pool is exhausted and no LRK
SK  = KDF(DH1 ‖ DH2 ‖ DH3 ‖ DH4)
```
`SK` seeds the Double Ratchet. The first ciphertext is a **PreKey message** (libsignal type `3`)
carrying `EK_A` and the consumed prekey ids so the recipient reconstructs the same `SK`. Handled by
`SessionBuilder.processPreKey` / `SessionCipher` in
[`lib/secretSession.ts`](../front/src/features/e2ee/lib/secretSession.ts) (`ensureSessions`,
`encryptTo`, `decryptFrom`).

**Why the OPK:** it makes the *initial* handshake one-time — replay protection and stronger forward
secrecy for the first message. Its omission (exhausted pool) degrades gracefully to SPK-only, which
is X3DH's specified fallback (§6).

---

## 4. Ongoing messages — Double Ratchet

After X3DH, every message advances the **Double Ratchet**
([spec](https://signal.org/docs/specifications/doubleratchet/)): a symmetric-key ratchet for each
message plus a Diffie-Hellman ratchet on reply, giving **forward secrecy** (past messages stay safe
if a current key leaks) and **post-compromise security** (the chain self-heals after a leak). The
ratchet keeps its own ephemeral DH keys — it needs **no** prekeys from the pool. One ratchet session
exists **per (peer, device)** and is reused for the life of the conversation.

## 5. Safety numbers (out-of-band MITM check)

[`lib/safetyNumber.ts`](../front/src/features/e2ee/lib/safetyNumber.ts). A fingerprint derived from
**both** parties' public **IK** via libsignal's `FingerprintGenerator`, so it is identical on both
sides *iff* neither identity key was substituted. Users compare it in person / over a call and mark
the peer **verified**.

- **Symmetric:** the two `(userId, IK)` pairs are ordered by `userId` before hashing, so both sides
  compute the same string regardless of who runs it.
- **Work factor:** the spec uses 5200 iterations; this pure-JS port runs them sequentially (seconds),
  so we use **1024** — instant, and since *both* clients use the same constant the numbers still
  match. (Deliberately **not** interoperable with Signal's own app; we don't need that.)
- **Verification lifecycle:** the verified number is stored (localStorage). `isVerified` holds only
  while the stored number still equals the current one — so a later **IK change** (a peer reinstall)
  changes the number and **auto-drops** verification, prompting re-verify.
- **Only IK moves the number.** SPK rotation and OPK/LRK churn do **not** change the safety number.

Background: [Signal — Safety number updates](https://signal.org/blog/safety-number-updates/).

## 6. One-time-prekey lifecycle & prekey exhaustion

Constants (`provisioning.ts`): seed `OPK_BATCH=20`, target `OPK_TARGET=20`, low-water
`OPK_LOW_WATER=5`.

- **Consumption:** each *fetch* of a peer's bundle consumes one OPK **per device** server-side
  (`FetchAndConsume` serves the lowest-id OPK and deletes it). OPKs are meant to be spent **once per
  session establishment** — the sender **cache** (§8) ensures that, rather than one per message.
- **Replenishment:** `maybeReplenish` tops the pool **up to** the target when the server-reported
  `remaining ≤ low-water`. Triggered at startup **and on-demand** while active (so a fast drain
  refills without waiting for a relaunch).
- **Exhaustion (prekey-exhaustion attack):** because any authenticated caller can fetch, a peer's
  pool can be drained. When empty:
  - if a **last-resort prekey (LRK)** is published, the directory serves it **without consuming it**
    (reusable), so X3DH keeps its full 4-DH shape;
  - otherwise `oneTimePreKey` is `null` and X3DH falls back to **SPK-only** (`DH1..DH3`).
  Either way the session still establishes and stays E2EE. A reused LRK is cryptographically
  **equivalent to** the SPK-only fallback (it loses the one-time replay/FS property once reused);
  its value is a uniform handshake shape and an independently-rotatable reusable key. **Only real
  replenishment restores per-handshake one-timeness.**
- **Rate limiting:** the `KEY_FETCH` endpoint is per-caller rate-limited (`KD_FETCH_RATE_PER_MIN`,
  burst) and requires an authenticated session, bounding drain speed.

## 7. At-rest plaintext & message loss states

[`lib/atRest.ts`](../front/src/features/e2ee/lib/atRest.ts),
[`lib/failure.ts`](../front/src/features/e2ee/lib/failure.ts).

Server history is **ciphertext**. Your *own sent* messages are encrypted to the peer's key — you
cannot re-derive them; incoming ones you decrypted once, but the ratchet has since advanced. So
decrypted plaintext is cached **locally** in an `e2ee-plaintext` IndexedDB store, wrapped under the
device-key, keyed by message id, with a **7-day TTL** (disappearing messages). After the TTL the
plaintext is swept.

Message decryption states shown in history:

| State | Meaning |
|---|---|
| **expired** (`aged`) | older than the 7-day TTL; plaintext purged **by design** — not an error, no recovery attempted |
| **pending** | recoverable; a recovery re-request is in flight (§ below) |
| **unavailable** | our own message; nothing to recover from |
| **lost** | all decryption **and** recovery attempts failed — a genuine failure |

**Recovery** ([`recovery/`](../front/src/features/e2ee/recovery/)): a receiver that cannot decrypt a
*received* message re-requests it from the **original sender** over a **dedicated orthogonal
recovery session** (`RECOVERY_DEVICE_ID = 0x5EC0`) that is torn down and re-established per batch, so
its first message is a clean PreKey message with no ratchet gap to cross. The recovered plaintext is
**AEAD-bound** to `(messageId, chatId)` *inside* the ciphertext and checked against a
recipient-binding, so a tampered response cannot relabel one message as another. The recovery window
is 7 days (matching the TTL); beyond it, messages read **expired**, not **lost**.

## 8. Multi-device model — serve-all, encrypt-to-all, lazy resolution

Signal is **pairwise**: ciphertext is addressed to a **device**, not a user. Hormiga's model
(as-built + [`e2ee-device-resolution`](../openspec/changes/e2ee-device-resolution/proposal.md)):

**Envelope** (`secretSession.SecretEnvelope`) carries one ciphertext **per recipient device**:
```jsonc
{ "v":1, "alg":"signal", "from": senderDeviceId,
  "to": { "<recipientDeviceId>": { "t": msgType, "b": ciphertext }, ... } }
```
A device decrypts only the entry addressed to its own `deviceId`; it *cannot* read another's — it
has no keys for that session (the addressing is convenience; the crypto is the guarantee).

**Directory contract** (`hormiga-key-directory`):
- **Fetch serves *all* of a user's devices**; the sender **encrypts to each** (`FetchAndConsume`
  with empty deviceId returns every device).
- **Publish never retires siblings** (append/upsert) — the regression that deleted sibling devices
  and made messages undecryptable is gone.
- **Stale-device GC — keep-newest:** a background sweep prunes a device only if it is older than the
  device TTL (**60 days**) **and** the user has a newer device. A user's single dormant device is
  **never** pruned (a first contact must always find ≥1 bundle). Live devices stay fresh via the
  client's touch-on-start republish.

**Sender-side caching + lazy device discovery** (the efficiency + correctness core):

1. The sender **caches** the peer's device roster + established sessions. A send that has live
   cached sessions uses them directly — **no directory fetch, no OPK consumed** (fixing the former
   per-message OPK burn).
2. It **encrypts to all cached devices** (usually one).
3. If the peer switches devices, the new device receives an envelope with **no entry for its own
   deviceId**. It emits a **metadata-only "rekey hint"** to the sender — no key material, no device
   address, just "re-resolve me in this chat".
4. On the hint the sender **invalidates its cache**, **re-fetches from the trusted directory**
   (bypassing the cache), establishes sessions to the now-known devices, **encrypts to all**, and
   **resends**. Durable dedup prevents a double if the old device was still live.
5. Cache also invalidates on **roster TTL** (24h) and on a **local decrypt failure** (peer identity
   changed → reinstall).

**Rekey-hint safety:** the hint is only a *trigger to re-resolve* from the directory, whose publish
is auth-bound to the caller's `userId` (Oathkeeper). A spoofed hint can at most cause a
(rate-limited) spurious re-fetch — it can never inject an attacker device. Hints are coalesced (one
re-resolve per peer per burst).

This is **lazily-discovered multi-device**: after one round-trip the sender knows every live device
and delivers to all of them, so parallel devices work and a device switch heals itself — without
Signal's eager fan-out to every device on every send. See Signal's multi-device design
([Sesame spec](https://signal.org/docs/specifications/sesame/)) for the eager alternative.

## 9. Calls — end-to-end-authenticated signaling over ephemeral TURN

See [`e2ee-call-signaling`](../openspec/changes/e2ee-call-signaling/proposal.md) and
[`features/call/service/`](../front/src/features/call/service/).

- **Media** is encrypted by **DTLS-SRTP** inherently (WebRTC): the relay (coturn) only forwards
  ciphertext and cannot decrypt. See [RFC 8827 — WebRTC Security Architecture](https://www.rfc-editor.org/rfc/rfc8827)
  and [RFC 5763/5764 — DTLS-SRTP](https://www.rfc-editor.org/rfc/rfc5763).
- **Signaling gap:** the SDP offer/answer carries `a=fingerprint` (the hash committing to each
  peer's DTLS cert). A malicious server could rewrite it and MITM the DTLS handshake. Fix: **wrap
  the SDP inside the Signal session** (`webRTCService` encrypt-on-send / decrypt-on-receive). The
  server sees only ciphertext; the browser's DTLS stack verifies the peer cert against the
  now-authenticated fingerprint. **Fail-closed:** no plaintext-SDP fallback (a fallback would let
  the server force a downgrade).
- **TURN is ephemeral** ([`iceConfig.ts`](../front/src/features/call/service/iceConfig.ts),
  [`shared/config/webrtc.ts`](../front/src/shared/config/webrtc.ts)): the client fetches short-lived
  credentials from `GET /key-directory/v1/turn/credentials`; the directory mints
  `username = <expiry>:<userId>`, `credential = base64(HMAC-SHA1(TURN_SECRET, username))`, which
  coturn validates via `use-auth-secret`. No long-lived shared credentials; own STUN only. See the
  [TURN REST API draft](https://datatracker.ietf.org/doc/html/draft-uberti-behave-turn-rest-00) and
  [RFC 8656 — TURN](https://www.rfc-editor.org/rfc/rfc8656).

## 10. Key directory service (`hormiga-key-directory`)

A small Go service that stores/serves **public** keys only and does **no** cryptography.

- **Auth:** network-isolated behind Oathkeeper, which authenticates the Kratos session
  (`cookie_session`) and injects `X-User-Id`. Publish is bound to the caller's own id.
- **Endpoints:** `POST /v1/keys` (publish), `POST /v1/keys/one-time` (replenish),
  `GET /v1/keys/self/count`, `GET /v1/keys/{userId}` and `/{userId}/{deviceId}` (fetch, rate-limited,
  consumes an OPK/device), `DELETE /v1/keys/self/{deviceId}`, `GET /v1/turn/credentials`.
- **Stores:** Postgres (prod) and an in-memory store (dev/e2e), behind one interface with parity.
  FK `ON DELETE CASCADE` from prekeys → identity; `updated_at` per device drives keep-newest GC.
- **Config:** `KD_DEVICE_TTL_DAYS` (default 60), `KD_GC_INTERVAL_HOURS` (24),
  `KD_FETCH_RATE_PER_MIN`/`KD_FETCH_BURST`, `KD_TURN_SECRET`/`KD_TURN_URIS`/`KD_TURN_TTL_SECONDS`.

## 11. Deliberately deferred

- **PQXDH** (post-quantum X3DH, [spec](https://signal.org/docs/specifications/pqxdh/)) — deferred;
  the current handshake is classical X3DH.
- **Encrypt-to-self** — a sender does not encrypt a copy to its *own* other devices, so a second
  personal device does not see history sent from the first. Simpler, security-first.
- **Eager multi-device fan-out** (Signal/Sesame style, all devices every send) — we use lazy
  discovery instead.
